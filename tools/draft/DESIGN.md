# draft

Run `draft new <dir> "<what you want>"` and get a `DESIGN.md` you can argue
with. Run `draft check` and find out whether it is buildable. Run
`draft build` and let its own check decide when it is done.

## What it is

The fifth verb, and a shell script. `ask` has the model, `brief` has the
procedure, `ply` has the loop, `hone` has the lesson — and between them
there was nothing that decided *what to build*. `draft` is that: it owns
one document, `DESIGN.md`, which is simultaneously the requirements, the
procedure a builder follows, and the definition of done.

It holds one opinion, and everything else follows from it: **a design that
cannot say how you would know it worked is not a design.** So `DESIGN.md`
must name a shell command whose exit status is the verdict. `draft check`
refuses a design without one. `draft build` hands exactly that command to
`ply` as `-check`.

## Requirements

- [x] A design is refused unless it names a real check — not prose, a command.
- [x] The design is one file a human reads, edits, and argues with. Not a
      transcript, not a config format, not a wizard.
- [x] Knowledge of the four tools is generated from the installed binaries,
      never written by hand, and staleness is a program's opinion.
- [x] `draft` adds no capability of its own. It composes the four and holds
      no model, no loop, no catalogue, and no state.
- [x] It works from a checkout with nothing installed but the four tools.
- [x] Every refusal names what is wrong and what to do about it.

## Not doing

- **A binary.** The other four are Go because each had something genuinely
  hard in it. `draft` composes, and composition in this family is a file —
  which is the conclusion the substrate review reached and deferred.
- **An interactive interview.** `ask` cannot ask a clarifying question and
  `ply` gives commands `/dev/null` on stdin. The human-in-the-middle *is*
  the interview: a model drafts, you edit, `check` decides. The artifact is
  a document rather than a conversation, which is the point.
- **A code generator.** `draft build` is `ply` with a check. There are no
  templates for the system being built, because a template is a guess about
  a problem nobody has described yet.
- **A registry, a config file, a daemon, a cache, or state of any kind.**
  The design is the state and it is in the project directory.
- **Execution policy in `brief` frontmatter.** Deferred deliberately in
  `brief/AGENTS.md`; a capability is a file until that demonstrably hurts.
- **Its own model or provider code.** If it needs a model it runs `ask`, in
  a session under `<dir>/.draft` so the design's reasoning replays.

## The split

| stage | tool | why |
| --- | --- | --- |
| scaffold, extract the check, verify sections, compare the reference | none -- a script | text and exit statuses; no judgment anywhere in it |
| generate the tool reference | none -- a script | the binaries already print the truth; `sync` only collects it |
| fill the template from a description | ask | one question, one shape, no loop -- and it is optional |
| build the system the design describes | ply | the design names a check, which is precisely what `ply` needs |
| learn from a build that stumbled and recovered | hone | only when a build does; not wired in, and not forced |

## Data

    raw:
      DESIGN.md                 the agreement. Written or edited by a human
      <dir>/.draft/design.jsonl the ask session that drafted it; replayable

    derived:
      skills/draft/references/tools.md   generated by `draft sync`

`tools.md` is derived from the installed binaries, so it is never edited and
always rebuildable. `draft check` regenerates it into a temporary file and
compares, which is the same code path `sync` uses — two ways to decide
whether it had drifted would eventually disagree.

## Check

```sh
sh -n bin/draft && sh bin/draft_test.sh && brief lint -strict skills/draft
```

The suite runs no model and reaches no network. It covers the Unix contract,
the falsifiability gate in both directions, that the template `new` writes is
the skill's own copy rather than a second one that could drift, and that
`SKILL.md` names every file in `references/` — because progressive disclosure
silently drops a reference nothing mentions.

## Prove

`draft check` refuses a design with no check, and `ply` drives until the
check passes. Neither says the check is adequate, and it is written by the
same model that wrote the code — so it tests only the states that model
imagined. One system built here passed a genuinely thorough check and then
downloaded 190 MB on its first real run, because the empty-store path was
the one its fixtures never created.

So `draft prove` mutates the code and reports what the check let through.
It is mechanical: six semantic operator flips, no model, a program's
opinion. Killed-versus-survived is the number; the distribution across
files is the useful part.

It found seven bugs in itself by being run, and each is now a rule:

- writes go through a sibling temporary and a rename, and the original is
  journalled in the project — `sed > file` truncated a source to zero bytes
  when a kill landed in the window between open and write;
- compiled bytecode is scrubbed after every restore, because `==` and `!=`
  are the same length and Python's `(mtime, size)` invalidation missed a
  mutant that then poisoned the *next* measurement;
- each run is bounded and runs in its own process group, because a mutant
  that removes a loop's exit condition hangs rather than fails, and killing
  the shell leaves the interpreter running;
- the sample is collected whole and strided, because walking files until a
  cap trips measures one file and reports it as a project;
- the cap is met exactly rather than undershot by integer division;
- data files are chosen by allowlist, since a `.jsonl` walked through an
  exclusion list that named `.json`;
- the journal is removed on success, or the next run "recovers" a file that
  was never damaged.

      DESIGN.md
      README.md
      justfile
      bin/
        draft              the capability: new, check, prove, build, sync
        draft_test.sh      the check

## Traps

- **`ply system` reports the prompt for the flags it is given.** An early
  `draft build` composed `ply system` output into `-S` without `-sh`, so the
  model was handed a prompt saying it had no tools and spent its first turn
  explaining it could not reach a filesystem it had. `draft` no longer
  rebuilds the prompt at all: `ply` owns it, the design stays a file the
  model reads, and `-s draft` appends the doctrine through `brief`.
- **The design stays out of argv.** `ps(1)` is world-readable and a design
  can be private, so `build` tells the model to read `DESIGN.md` rather than
  embedding it in a flag.
- **`draft new` must pass `ask -n`.** Otherwise drafting a design continues
  whatever conversation you were having at your terminal.
- **The test suite needs the four tools on PATH** and says so once, at the
  top, because `draft check` cannot call a design buildable without the
  tools that would build it. Eleven obscure failures reporting "21 passed"
  reads like success, and that is worse than a refusal.
- **`draft check` is `grep`'s contract, not `ask`'s.** Exit 1 means *no, not
  buildable* — an ordinary answer a script branches on. Exit 2 means broken.
