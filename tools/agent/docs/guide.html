Normal setup is source-free, platform-aware, and part of the same tutorial.

On supported macOS and Linux hosts, the builder asks the steward procedure to select the exact arm64 or amd64 suite archive, show the helper’s embedded reviewed SHA-256, prefix, writes, and rollback, and request one decision. The helper downloads only that archive and verifies it against the pin before extraction; it does not fetch a checksum sidecar. After approval it installs through the verified archive’s own atomic installer and checks the complete suite. It then shows a second, bounded Cage plan—temporary fixtures, loopback only, no credentials—and requests approval for the target-host enforcement check before returning to the saved build gate. No Go toolchain or repository clone is needed. Building from an exact, clean release checkout is a separate explicitly chosen engineering path—never silent recovery.

Setup uses evidence-backed states—no optimistic green lights.

SUITE-INSTALLED means the exact suite, public commands, and checksums are verified and a Cage backend is present. SUITE-READY additionally means the separately disclosed target-host cage check passed 13/13. A nested Claude or Cowork sandbox may block that kernel-level test; then Claude reports CAGE-HOST-CHECK-REQUIRED and gives one exact command to paste into a terminal on the target machine. MODEL-READY separately means the selected non-secret provider/model and approved controller-owned access completed one timeout-bounded, schema-constrained Ask call in this lane; configured credentials alone are not proof. AGENT-FIRST-RUN means a checked Agent home completed one bounded bench home run and retained its literal result. Every completed state and the exact resume gate survive a blocked check.

Before the interview

Bring evidence of the work, not a perfect specification.

Claude should help you make tacit knowledge explicit. It should never quietly fill missing policy with plausible prose. A small, real process pack gives the conversation something concrete to examine.

1

Representative cases

Bring a few normal examples, edge cases, failures, and corrected outputs. Remove secrets and use test copies.

2

Authoritative sources

Policies, records, forms, and systems—plus who owns each one, how fresh it must be, and which wins in a conflict.

3

Decision owners

Name who can settle ambiguous rules, approve the design, judge withheld cases, and accept the pilot risk.

4

Known exceptions

What makes experienced people pause? Include incomplete, conflicting, stale, unusual, and adversarial inputs.

5

Current handoffs

Show where the job begins, what it produces, who receives it, and what happens when it cannot finish safely.

6

Risk boundaries

Separate what the system may read, recommend, draft, propose, affect with approval, and never do.

Choose a narrow first job.

  • Frequent enough to learn from quickly
  • Bounded by a clear trigger and handoff
  • Observable by a knowledgeable reviewer
  • Grounded in available digital evidence
  • Reversible before consequential effects
  • Valuable after review and operating cost
  • Not “handle all of finance” or another broad mandate
  • Not a rare, unexplained, irreversible, or ownerless process

The tutorial

Build in nine reviewed gates.

The skill handles mechanics and asks one decision-sized question at a time. You remain responsible for the business meaning. Each gate produces an artifact another person can inspect without replaying the chat.

Start here · natural language works in Cowork and Claude Code
Use the Building with Bench skill. I own [name the process] and want to build a narrow Bench system for [business outcome]. Work in this dedicated project folder.

Begin with read-only preflight. Classify this session as BUILD-READY, DESIGN-ONLY, or STEWARD-REQUIRED and show the evidence for that classification. Do not install software, authenticate, schedule work, execute an external effect, or widen permissions during preflight.

After preflight, keep this as one continuous setup-to-run journey. If this is a supported local host and the exact suite is missing, show one pinned steward install plan, ask me to approve its exact changes, verify it, and resume the saved build gate. Report SUITE-INSTALLED after exact byte and command verification; report SUITE-READY only after the separately disclosed target-host Cage check passes 13/13. If this nested interface blocks that check, report CAGE-HOST-CHECK-REQUIRED with one exact command for my host terminal and preserve the resume gate. Then show the bounded model-readiness probe plan and ask for approval before its one provider call. Report MODEL-READY only from its literal pass, or MODEL-ACCESS-REQUIRED before any model-backed Bench or Draft command. My Claude login or configured credential is not proof that Ask can reach a provider. If access is unavailable, preserve the exact blocked gate and resume command instead of restarting. Use only the Bench suite’s Agent system.

Then guide me one decision-sized question at a time. Preserve approved decisions in a new bench-system/ process pack. Do not invent policy, source precedence, expected answers, thresholds, or authority. Stop for my review at every gate, keep withheld answers outside the worker-readable folder, and distinguish clearly among SUITE-INSTALLED, SUITE-READY, MODEL-READY, AGENT-FIRST-RUN, design complete, structure valid, check proved, and pilot ready. End with a concrete local runbook.

01

Claude observes · you confirm

Classify the execution lane.

The skill first examines only safe, visible facts: workspace, operating surface, suite commands and versions, Cage backend discovery, and whether the user authorized build work. It does not install, authenticate, or inspect secret values. An approved target-host Cage test is a separate step because discovery is not proof of enforcement. After that setup, the skill shows one bounded model-readiness plan—empty system prompt, no tools or attachments, constant schema, 60-second timeout—and asks before calling Bench Ask.

What you review

  • Where the work runs
  • Which folder is dedicated to it
  • Whether the pinned suite is reachable
  • Whether the lane is build-ready, design-only, or steward-required

Why this gate matters

Without it, an interface may produce polished design files and accidentally describe them as a built agent. The classification creates an honest claim boundary before momentum makes that distinction inconvenient.

Result: a stated execution lane and supporting observations. On a supported local host with no suite, Claude continues in this same journey: it previews one pinned install, asks for approval, verifies the suite as SUITE-INSTALLED, then presents the bounded Cage proof and records SUITE-READY only after its 13/13 target-host pass. It records MODEL-READY only after the separate Ask probe succeeds in this lane. A declined, unsupported, cloud-only, Cage-host-blocked, or provider-blocked setup preserves the exact missing claim, owner, and resume command rather than discarding completed work.
02

You define · Claude records

Frame one accountable job.

Describe a finished business state, not a personality or a broad aspiration. The builder fills 00-job-brief.md and refuses to hide unresolved ownership inside “the agent will decide.”

When [trigger] happens, use [trusted inputs] to produce or do [result]. Success means [observable evidence]. Never [boundary]. Escalate when [condition].

Useful owner questions

  • Who is accountable if the result is wrong?
  • What exact handoff marks the job complete?
  • What must remain a human decision?
  • When is no answer safer than a guess?

A subtle but important test

If two experienced people disagree, ask what evidence or authority settles the disagreement. “Use good judgment” is not yet an operating rule; it may be a rubric, an example boundary, or a mandatory escalation.

Result: an owned job brief with trigger, outcome, boundaries, evidence, escalation, and explicit non-goals.
03

You teach · Claude structures

Map the real decisions and exceptions.

Walk through the normal path, then contrast near-neighbors: one acceptable example and one that looks similar but should be handled differently. The builder records the process in 01-process-map.md.

Explain what experts notice

Thresholds, timing, missing fields, source conflicts, unusual combinations, customer or policy context, and the signals that cause a pause or escalation.

Do not automate confusion

When the team itself cannot explain a decision consistently, mark it as an unresolved policy question. An agent can expose that gap; it cannot legitimately settle it by sounding confident.

Result: a process map whose decision points, failure paths, and stop conditions are reviewable by the people who do the work.
04

You supply truth · Claude builds the registers

Separate examples, evidence, and authority.

These are three different control problems. The skill creates a case library, source register, and authority register rather than burying them in one long prompt.

Case library

Include teaching, regression, edge, adversarial, and withheld case IDs. Keep withheld inputs and expected answers outside every worker-readable root.

Source register

For each resource: owner, authority, freshness, conflict order, sensitivity, and what happens when it is absent or stale.

Authority register

Classify each capability as read, recommend, draft, propose, affect, or forbidden—with approval and uncertainty behavior.

Why separation matters

A system may know the right answer yet lack permission to act; have permission yet rely on stale evidence; or pass examples it was allowed to memorize. One “confidence” score cannot diagnose those failures.

Result: 02-case-library.csv, 03-source-register.csv, and 04-authority-register.csv.
05

Claude proposes · you approve ownership

Compose the smallest complete Bench system.

Using the full platform does not mean running every component on every turn. It means every guarantee has a named owner instead of being silently assigned to the model. The builder fills 05-system-design.md and explains every inclusion and omission.

Bench contract→Draft design→Build→Prove→Agent home→controlled pilot

Keep different owners distinct

Deterministic transformation, model judgment, evidence retrieval, credentialed effect execution, human approval, supervision, and acceptance should not collapse into one model call.

Start with less authority

A read-only recommendation or a saved draft often proves the business value with far less risk. Add one capability boundary at a time after regression evidence remains strong.

Result: a reviewed composition, responsibility map, budgets, boundaries, assumptions, and explicit reasons for what is not yet included.
06

You define success · an external judge enforces it

Design proof before model work.

The author of a candidate result must not be its sole judge. The builder fills 06-proof-plan.md with exact checks, withheld cases, a calibrated human rubric where needed, failure cases, thresholds, budgets, and claim limits.

structure

Is the home valid?

Offline checks verify required files and contracts—not business correctness.

mutation

Can the check detect damage?

Draft Prove challenges the executable check with meaningful faults.

withheld outcomes

Does it do the unseen job?

An external harness compares outputs with an oracle the worker cannot read.

pilot

Does it improve reality?

Bounded use measures utility, review burden, errors, escalation, cost, and drift.

A passing schema is not a useful agent.

Reject constant checks, checks the worker controls, placeholder goals, model self-grading, and demonstrations presented as holdouts. Record what every check proves—and what it does not.

Result: a proof plan that can fail the system for meaningful reasons before anyone spends trust on a pilot.
07

Only in a build-ready lane

Materialize the durable Agent home.

Claude shows the proposed build sequence and obtains approval before writes or model-backed work. It uses bench home new to create one Bench Agent home—never a Claude-native worker or a parallel agent format—then maps the reviewed goal, procedure, skills, tools, check, and optional wake gate into their owning files.

Definition plane

Reviewed job, invariants, skills, toolbox, cadence, specialists, and policy. The worker cannot quietly rewrite its constitution.

Mutable work and state

Drafts, checkpoints, queues, and continuity records live in explicitly writable areas with bounded semantics.

Independent check

An executable controller-owned program accepts, rejects, or reports verifier failure. Its expected labels remain outside the worker’s view.

Controller evidence

Receipts, run history, proposals, decisions, versions, and verdicts stay separate from candidate work.

Design-only users stop correctly here.

The skill creates STEWARD-HANDOFF.md with exact missing capabilities, expected versions, validation commands, risk, owner, and restart point. That is a complete design outcome—not a failed conversation and not a built worker.

Then prove it and run it once.

Claude runs bench home check and show, proves accepted and rejected check fixtures, and proves quiet/wake/broken behavior when recurring work is needed. With MODEL-READY, it makes one effect-free fixture run: the controller may reach the selected model provider, while the worker receives no general network grant. It records AGENT-FIRST-RUN plus the literal outcome in FIRST-RUN-REPORT.md. Without provider access, it records MODEL-ACCESS-REQUIRED and the exact command to resume after the named owner supplies the approved boundary.

Result: BUILD-READY plus MODEL-READY produces a proved home, one bounded first local run, and commands the owner can use immediately. A provider-blocked lane preserves the reviewed process/design package, every offline artifact actually completed, and the exact resume gate without claiming a checked build or first run; DESIGN-ONLY produces a complete handoff without making an execution claim.
08

Platform steward connects · business owner rechecks

Add evidence and effects through explicit edges.

Begin with fixtures, then read-only sources. Credentials stay controller-owned and outside chat, argv, logs, and the Agent home. An intended real-world effect becomes a strict proposal evaluated by policy, exact human review when required, a narrow connector, and a durable receipt.

Evidence plane

Context normalizes records; Cite checks exact reference identity; MCP capabilities are discovered, reviewed, digest-admitted, and scoped. The business design still owns source authority.

Effect plane

Action owns policy, conditional May review, connector execution, typed receipts, and unknown outcomes. A worker request is never itself permission.

read→recommend→draft→propose→approved effect
Tool selection is not isolation.

A toolbox, Cage boundary, Claude approval dialog, OAuth scope, and Action receipt answer different questions. Review ambient host reads, writes, network, identity, and credentials independently.

Result: reviewed source and capability edges, no secret values in project artifacts, and a rerun of every affected regression case.
09

You accept · operations remain bounded

Run a controlled pilot, then operate a lifecycle.

Fill 07-pilot-plan.md. Start in simulation, shadow, or draft-only mode. Bound the population, volume, duration, review cadence, escalation threshold, pause rule, rollback, owner, and retirement path.

Track useful signals

Unseen-case quality, safe escalation, correction rate, false success, review burden, source failures, cost, latency, effect uncertainty, and whether confidence matches actual performance.

Change one boundary at a time

A new procedure, source, model, check, permission, connector, or schedule is a system change. Review the diff and rerun the relevant full regression set before promotion.

Pause safely

Stop new work, preserve evidence, inspect running or unknown outcomes, revoke unneeded effects, and avoid automatic retry where an external action may already have happened.

Retire deliberately

Disable schedules, reconcile open work, revoke credentials and connector grants, record the last definition and verdict, and apply explicit evidence retention.

Result: one honest readiness state—design complete, structure valid, check proved, or pilot ready—plus a named owner and smallest next decision.

The product question

Can business users build good agents now?

Yes, for a useful prototype and controlled pilot—with a prepared runtime and shared ownership. The new skills remove the need to read Bench source and make the business-to-system method portable. They do not yet make consequential production operation fully self-service.

P0 · execution bridge

A managed Cowork runtime

The largest remaining gap is a first-class Bench integration that exposes versioned, typed lifecycle operations to Cowork without relying on ambiguous host shell access.

  • Preflight with explicit execution and persistence claims
  • Contract review, Draft build/prove, Agent compile/check/run
  • Rendered diffs, evidence, safe next actions, and typed failures
  • Strong identity, isolation, budgets, and durable effect state
P0 · quality UX

No-code cases and checks

Business owners need a worksheet-to-evaluation experience that helps them create useful oracles without pretending every judgment is mechanical.

  • Teaching and withheld separation by construction
  • Contrastive examples, calibrated rubrics, and coverage
  • False-success, escalation, adversarial, and mutation cases
  • Visible readiness states instead of one green badge
P0 · credential boundary

Controller-owned model and connector access

Unattended local Agent work still needs a first-class way to give Ask a provider credential without placing that value where a model-authored action can read it. A generated environment file is not that boundary.

  • Credential delivery through a broker or one-child seam
  • Fresh-process identity preview, rotation, and revocation
  • Scoped MCP and OAuth setup without exposing values
  • Action policy, exact review, receipts, and unknown reconciliation
P1 · ownership

An operator cockpit

One view should answer what the worker owes, what it can do, what happened, what is waiting, and whether quality is changing.

  • Goal, definition version, schedule, state, and last verdict
  • Pending decisions, proposals, incidents, and unknown effects
  • Case performance, corrections, source use, cost, and latency
  • Safe change, regression comparison, pause, rollback, and retire
P0 · unattended controls

A production schedule controller

The included renderer gets a local pilot to a reviewable disabled timer. Consequential unattended work still needs one controller that enforces the whole operating envelope.

  • Maximum duration and model/effect budgets
  • Overlap, catch-up, pause, and backpressure policy
  • Log rotation, retention, health, and failure notification
  • Fresh-process provider identity without readable secret values
P1 · supply chain

Signed, administered distribution

Checksums are a sound starting point. Enterprise adoption also benefits from signed releases, provenance, an SBOM, centrally pinned plugin versions, policy review, and managed updates.

research · sustained use

Test ownership, not demo success

Ask process experts to diagnose an unfamiliar failure, change a policy without regressing holdouts, explain evidence and authority, and retire the system. Time to a polished first output is not enough.
