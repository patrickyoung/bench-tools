# Touchline — an EPL scouting showcase

Build a polished, interactive scouting showcase as one HTML file that opens
offline. Its audience is a football recruitment analyst deciding whom to watch
next. This is a demonstration of the page-building team, not a live scouting
service or a claim about real players.

Use clearly labelled illustrative player profiles and statistics. Show the
sample-data status near the first useful scouting surface. Do not invent
sources, real player measurements, live feeds, or verified transfer valuations.
If using factual football claims, supply their actual source and observation
date. No external service is needed for this demo.

The page should feel like an editorial scouting desk: confident typography,
strong spatial composition, a dark football atmosphere, warm paper reading
surfaces, and a restrained luminous accent. Avoid a wall of identical cards.
The specialist team may refine this direction and must record its decisions.

Required journey:

1. Understand the scouting proposition and sample-data boundary immediately.
2. Search a compact set of player profiles and filter by position and age.
3. Open a profile with meaningful strengths, uncertainties, metrics and a
   suggested next scouting action.
4. Compare at least two selected profiles with consistent metric units.
5. Save/remove a player from a local shortlist and see the state update.

Use Blender for a purposeful spatial asset, image generation for an original
football visual, and GIMP for deliberate compositing or finishing. Save the
masters and production evidence beside the run. The final page must actually
use the assets. The visual artist should create a tasteful Three.js background
or a suitable equivalent whose motion supports the scouting concept. Include
reduced-motion handling and a usable fallback when WebGL is unavailable.

The frontend expert should assemble the whole experience into one distributable
HTML file with embedded CSS, JavaScript, assets, and any required libraries.
No CDN, external font, image URL, module fetch, or backend may be required at
runtime. Keep the page usable on a narrow phone and a wide desktop, including
keyboard navigation, visible focus, readable contrast, and accessible controls.

Validate search, filters, profile opening/closing, comparison, shortlist state,
responsive layout, reduced motion, and the rendering fallback. Inspect actual
screenshots and report material visual defects. A nonempty HTML file, a valid
backlog, and a model's approval are not sufficient acceptance.

Deliver index.html plus the run's source masters, backlog, actual assignment
outcomes, test evidence, and a short explanation of each specialist's concrete
contribution. Leave the reusable worker capable of handling a different brief.
