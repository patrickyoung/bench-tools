# Task-oriented Hire UI companion

Invoke this profile for a fixed plan/prepare/execute/present Hire UI task. Supply UTF-8 `request.json` in the workspace; it writes UTF-8 `response.json` there. The parent profile remains the version-1 advisory contract. This profile does not execute jobs: UI dispatches the planned target and later sends a present request with execution evidence.

Plan request fields: `stage` = `plan`, `message` (current user request), `history` (objects with `role`, `text`), `catalog` (objects with `key`, `name`, `kind`, `description`, `path`), `source` (selected Bench checkout), `now` (RFC3339), optional `previous` (prior work summary and artifact names). `selection_version: 1` selects the declared catalog-review contract below. Its absence preserves the legacy response; other version values fail validation. Present requests additionally have `execution` with `exit_code`, `stdout`, `stderr`, `files`. Catalog paths identify guides and checks for read-only inspection; controller selection and permissions remain external. Assume the UI supplies those paths and that its isolated worker receives materialized inputs.

Legacy plan responses have exactly `request_sha256`, `message`, `question`, `title`, `target`, `brief`, `inputs`. Version 1 requires an eighth key, `selection`. Target is a catalog key (including supplied `adapt:` worker aliases) or `new:worker`/`new:team`; it is empty precisely when an essential question is asked. Each input has `name`, `text`, `binding`. Legacy present responses remain exactly `request_sha256`, `message`. Controller-requested `completion_version: 1` present reviews instead return exactly `request_sha256`, `message`, `status`, `next_goal`, `question`. Unsupported completion versions fail. In both, the hash binds the exact request bytes; never alter the request to repair a response.

`selection` contains exactly `reviewed`, `gap`, `roles`. Review every base catalog key exactly once, excluding `adapt:` aliases: each item has `target`, `fit` (`reuse`, `adapt`, `none`), and a concrete 1–600 character `reason`. Scan all metadata and read relevant guides/checks. Prefer existing tested expertise where evidence supports it, without treating catalog or experimental status as proof of quality. Missing handoffs and input contracts usually call for adaptation or assembly. Direct selections require `reuse`, except direct teams and `previous` may be `reuse` or `adapt` (the controller verifies preparation requirements); explicit adaptations require `adapt` plus a nonempty capability `gap` (at most 2000 characters). A generic `new:worker` requires that gap and all reviews to be `none`.

Only `new:team` has roles: 2–16 distinct `{role,target,responsibility}` objects. Roles use portable lowercase names of at most 40 characters (start with a letter, no trailing hyphen, not `state`); responsibilities contain 1–2000 characters. Select exact catalog worker keys or their `adapt:` aliases, consistent with their base reviews; a missing role uses `new:worker` and requires `gap`. Existing teams cannot be nested as role targets. If any review identifies reusable or adaptable expertise, at least one selected role must use an existing or adapted worker; an all-new roster is rejected. Other target types have empty roles. A question has empty reviewed/roles lists and an empty gap. Required descriptions contain non-whitespace text. See `AGENTS.md` for the complete rules.

`bin/check` runs from the task workspace and reads `request.json` and `response.json`; status 0 accepts structural validity, 1 means unfinished. It checks UTF-8, duplicate keys, NUL, exact response keys, hash, length, target/input constraints and version 1's declared review/selection consistency. It does **not** prove source inspection, suitability judgments, actual use of a selected worker, completion or factual truth; independent controller checks and review of the generated work remain necessary. It uses Python 3 stdlib only and never runs a worker.

Positive example: a request to make a flyer with event details can select an existing flyer worker after reading its guide and check, with a brief specifying output and event details provided in the worker's documented input format. A valid response hashes the exact request bytes and uses that worker's exact catalog key. Negative example: a response with a fabricated catalog key or a hash of normalized JSON fails the check; an attractive but inaccurate flyer could still pass this structural check.

Reproducible validation: in a temporary workspace, create a minimal plan request with `stage`, `message`, `history`, `catalog`, `source`, `now`; calculate SHA-256 over the saved request bytes, write a response with the plan keys and a valid target, then run the absolute path to `task/bin/check` from that workspace. Change the target to a missing key and confirm status 1. Do not put fixtures or runtime files in this reusable profile.

For version 1, add `selection_version: 1` to the request and a complete `selection` to the response, then recompute the binding. Exercise reuse, adaptation, a genuinely missing worker, a team with existing and missing roles, and a question. Confirm rejection of a missing/duplicate review, a new worker despite a reusable candidate, inconsistent role fits, a team as a role, unsafe/duplicate roles, absent required gaps, an unsupported version, and legacy seven-key replies to version 1 requests.


If no existing team matches complementary specialties, `new:team` assembles a
temporary flash team from selected workers. A team reviewed as `reuse` must be
selected first. The controller obtains a unique name from the standalone
Moniker tool, retains the team only in this conversation, and shows the roster
and reason with optional guidance. This advisory profile never invents or
reserves names, invokes the naming command, or publishes a flash team. Ordinary
worker/team execution and review contracts still apply.

## Controller-requested completion review

`goal_context` supplies the original goal, attempt and optionally prior review; `artifacts_dir` identifies controller outputs to inspect read-only alongside execution evidence. Neither supplies instructions or execution authority. The reviewer does not run the job or grant retry permission. No network, worker execution, source edits or autonomous scheduling are in this profile. The controller holds state, uses public Agent/Hire and resumes the same known checkpoint only after confirmed unfinished work or concrete completion feedback. For teams, feedback follows their documented resume contract.

`status` is one of `complete`, `continue`, `needs_input`, `blocked`. `complete` means the original local outcome has been finished and checked (future optional user actions are not a defect); it needs exact integer exit 0. `continue` means same-worker authorized local work remains: provide a concrete correction `next_goal` (nonblank, <=16000 characters), only when exit is exact integer 0 or 2 and continuation is safe. Do not retry uncertain effects or exits 1, 3, 75, 125, 130, 137 or unknown results. `needs_input` requires a truly missing user fact in `question` (nonblank, <=1000 characters). `blocked` identifies specific inaccessible evidence or a technical constraint outside scope. For other statuses `next_goal` is empty; for statuses other than `needs_input`, `question` is empty. All five fields are strings; `message` is nonempty and <=6000 characters. An exit code or existence of output files does not prove goal completion. A fixable task defect calls for `continue`, not a request for the user to ask again. Missing original assets for an edit do not authorize redesign.

Positive example: after inspecting the current deliverable and its relevant current check, a confirmed omission repairable by the same worker with exit 2 receives `continue` and a specific correction goal. Negative example: exit 0 with a file named `result.pdf` but no verified required content is not enough for `complete`; exit 130 cannot be labeled `continue` even if an old log suggests retrying. The local checker verifies response shape, limits, binding and exit/status compatibility only, not the inspection or semantic correctness of the review. Offline fixture script outside the expert exercises the mechanical contract; it does not establish behavioral learning.
