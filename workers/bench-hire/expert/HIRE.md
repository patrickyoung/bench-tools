# Hire CLI advisory note (2026-09-26)

Scope: selected Bench Hire sources `tools/hire/README.md`, `tools/hire/SECURITY.md`, `tools/hire/expert/AGENTS.md` (builder instructions), and `.agents/skills/bench/references/learn.md`. These are repo-relative references under the caller-selected `knowledge_source`; the supplied teaching copies were README.md, SECURITY.md, builder-AGENTS.md and learn.md. Confirm current source if the selected checkout differs. This note is knowledge for answering questions, not permission for bench-hire to run Hire, edit a definition or scan a home. Answer the specific question, not this whole note.

Hire is a headless CLI: `hire build` runs its builder expert through public Agent. There is no additional model client, runtime, scheduler, registry or built-in UI. The local UI separately invokes commands and reviews proposals. Reuse a suitable worker/team before building another. `HIRE_AGENT` selects the exact Agent executable; `AGENT_ASK` retains an existing Ask wrapper. No new login is created by default. Agent/Cage permissions and model selection belong to the caller; standalone Ply Cage flags are not Hire/Agent flags.

`hire new EXPERT 'goal'` scaffolds a default portable definition without a model; `hire new -home HOME` is for an existing recurring-home layout. Its `bin/check` is deliberately unfinished. `hire build -C EXISTING_WORKSPACE` writes `WORKSPACE/expert` and may revise an existing authoring expert. Goal comes from argv after `--`, `-goal-file`, or stdin; with an explicit goal extra stdin is evidence. Answer goes to stdout, progress to stderr, artifacts to the workspace. `-evidence DIR` keeps records outside work; otherwise evidence uses `HIRE_DIR/KEY` or `~/.hire/KEY`, keyed to the physical build workspace. State, model, effort, checkpoint and limits pass through Agent. Build starts work even when the definition already passes; `-B=false` permits a passing pre-check to skip model work. Outcome is Agent's exit: 2 unfinished, 130 interrupted; no automatic retry. A folder left after a stopped build is not success.

`hire verify EXPERT` requires a portable definition via `agent check`, a bounded nonempty README, and no `work/`, `state/` or `.agent/` inside it; it validates nested specialists and Brief procedures. Hire's *outer* build check uses this structural verification; it never executes the *generated worker's* `bin/check` and is not a quality test. Before a real Agent run, inspect generated code, test the worker's check on meaningful positive and negative cases, review semantics and fresh independent outputs. Runtime verification is outside action Cage: never execute unreviewed generated code with controller authority. A build/verify pass proves no live business outcome.

To teach supplied standards, examples or corrections, copy the definition into a separate authoring workspace and use Hire there. Retain concise source/date/scope and a route to load the lesson; preserve output and check contracts, review the delta, then evaluate fresh positive and unrelated cases proving the lesson loaded. Version/publish separately. Do not invent runtime directories inside the portable definition. Hone learning is different: it requires a real replay-checked fail-to-pass recovery, not a successful run or a chat acknowledgment. Source-based teaching needs no such recovery.

Existing recurring HOME only: `hire learn -why -into SKILL HOME HOME/.agent/runs/SESSION.jsonl` inspects without a model; `hire learn -into SKILL -prepare PROPOSAL HOME SESSION` prepares wording separately from the skill; `hire learn -show PROPOSAL HOME` reviews; `hire learn -admit PROPOSAL HOME` admits exact reviewed bytes, rejects stale state and makes no extra model call. Use a named skill, a regular same-home session and a home-local proposal name; never transplant sessions. Portable work uses public underlying tools with explicitly selected paths and approved wrapper. No automatic learning, home scan or credential scan.

Home-maintenance boundaries: `hire history` is read-only Trail/Ask inspection of the scoped home archive, which is sensitive and not redacted. `hire proposals` reviews exact patches read-only; `hire amend` is a controller write outside Cage, limited to one existing root definition file from `work/proposals/`, with an exact one-use May decision bound to current bytes/hash, then recheck/validation/rollback. Approval is not proof of wisdom. `hire actions` reviews strict `{version, connector, input}` proposals in `work/actions/` read-only; these convey no credentials, connector path, policy or authority. `hire act` is the controller's external effect through Action/May; exit 125 may mean effect occurred, so inspect receipts, never auto-retry. Advisory UI `revise_worker` only proposes a separate candidate; a button does not mean applied. Offer only allowed UI targets/action kinds, otherwise explain the supported next step.

`BENCH_WEIGH` unset/empty/0 is off, 1 permits new selection, other values are configuration errors. Enabling does not install, select a model, authenticate, authorize live evaluation or require Weigh. Preserve dependencies in unrelated revisions; off is neither forced deletion nor global sandbox, and a required runtime judgment must not silently pass or fall back when off.

For team authoring give outcome, capabilities, interfaces, handoffs and independent checks; use a manager and reusable `expert/agents/` children only when useful. The built team is not a scheduler. Agent runs, Weave selects ready work, Tend retains attempts; use an external controller if the boundary prevents child calls. Structure and actual specialist contribution/integrated quality are separate. Counterexample: a UI mention alone, or generic Ask/Ply/Agent troubleshooting, is not a reason to load this note. Positive example: “Why did hire verify pass when the drafted reply is wrong?” — distinguish outer structure check from the generated reply checker and recommend independent output review, not a rerun or a weakened check.
