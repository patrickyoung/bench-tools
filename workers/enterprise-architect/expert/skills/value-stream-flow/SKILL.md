# Value-stream flow

Use for slow demand-to-value, handoffs, platform enablement, dependency queues,
or modernization sequencing.

## Procedure

1. Set explicit start and end boundaries around customer/business demand and
   realized value, not merely code started and deployed.
2. Map work, wait states, queues, handoffs, approvals, rework, dependencies, and
   feedback loops. Identify owner and evidence source at each step.
3. Use supplied elapsed time, touch time, arrival rate, work in progress,
   failure/rework, and abandonment data. If unavailable, propose collection
   rather than manufacturing a map with numerical claims.
4. Find the constraining queue or dependency and its causes. Distinguish demand,
   capacity, batch size, environment, policy, architecture coupling, and missing
   self-service.
5. Compare reducing demand, simplifying controls, decoupling contracts,
   improving discoverability, or adding paved-road self-service. Do not automate
   waste or transfer toil to consumers.
6. Recommend one reversible increment with adoption support, feedback,
   acceptance evidence, owner, and review trigger. Measure end-to-end flow and
   outcome, not local activity alone.

## Platform enablement

A useful paved road has a clear consumer, discoverable contract, safe default,
fast onboarding, observable service promise, support path, escape hatch, and
measured friction. Test whether it reduces queueing and cognitive load without
concealing risk.

## Common failures

- Comparing teams by story points or treating points as productivity.
- Optimizing coding time while ignoring waits and benefit realization.
- Adding a central approval queue as governance.
- Assuming self-service means no support or decision rights.
- Declaring a bottleneck from anecdotes without confidence/evidence.
- Funding broad transformation before a small learning loop.
